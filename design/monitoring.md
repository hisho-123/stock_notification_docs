# 通知・日次処理仕様

## 最高値・下落率・通知条件

最高値`H`は登録時・日次処理で実際に取得した価格の最大値。最終取得値を`P`とすると下落率は`(H-P)/H×100`。`P>H`なら`H=P`へ更新し、最終通知済み率`L`を`null`に戻す。この実行では通知しない。

`P≤H`の場合、共通設定のうち`(H-P)×100 ≥ H×閾値`を満たす最大値を到達閾値`T`とする。到達値がなければ通知しない。`T>L`（`L=null`は0と扱う）の場合にだけ送信する。通知判定は十進数の丸め前の値で行い、表示用の下落率だけ小数2桁に四捨五入する。

価格0・負数・NaN・Infinityは使用しない。最高値と同じ価格に戻っても通知済み率はリセットしない。30%通知後にさらに下落しても、設定により大きい閾値がなければ追加通知しない。

## 通知例

以下は仕様説明用の仮の価格。

```text
株・指数の下落通知
銘柄: S&P 500 (^GSPC)
下落率: 27.00%
到達閾値: 25%
監視開始後の最高値: 6000
最終取得値: 4380
取得日時: 2026-10-08 07:00 JST
```

表示名、コード、下落率、到達閾値、最高値、最終取得値、取得日時を含める。価格は通貨換算せず、対象の提供価格の単位で扱う。LINEがHTTP 200で受け付けた場合を送信成功とする。ユーザーへの配信・既読は保証しない。

## 判定の具体例

初期設定は`[10,15,20,25,30]`、最高値100とする。各行は独立した例（「連続」行だけ順に実行）。

| 条件 | 結果 |
| --- | --- |
| 未通知、90.0001 | 下落率表示は10.00%でも丸め前は10%未満。通知しない |
| 未通知、90 | 10%を1通通知、通知済み率10 |
| 未通知、73 | 27%下落。25%を1通通知、通知済み率25 |
| 通知済み20、95→80（連続） | 回復後に再下落しても20%で再通知しない |
| 通知済み20、100 | 最高値と同値なので通知済み20を保持 |
| 通知済み20、110→99（連続） | 110で最高値更新・未通知に戻る。99で10%を通知 |
| 通知済み30、60 | 設定上の最大30%を超えても再通知しない |
| 通知済み20、設定を[5,15,25]へ変更、価格80 | 15%到達だが通知済み20以下。通知しない |
| 同じ設定変更後、価格75 | 25%を通知 |
| 停止中に価格70、再開後の日次取得価格85、通知済みnull | 停止中の70は扱わず、15%を通知 |
| 削除後に価格80で再登録 | 最高値80、未通知、下落率0.00%で開始 |

## 実行手順

外部スケジューラは毎日07:00（`Asia/Tokyo`）に`stock-notification monitor`を1回起動する。API経由の監視開始機能は設けない。

1. 必須設定とDB接続を確認する。PostgreSQLのセッション単位advisory lock（キー`7307001`）を`pg_try_advisory_lock`で取得する。取得不可なら重複実行として送信せず終了0。
2. 共通閾値を実行開始時に1回読み、全銘柄で同じスナップショットを使う。実行途中の設定変更は次回から適用する。
3. 有効な対象のID・コードをID順で読み、順番に処理する。対象0件は正常終了0。
4. FMPから一致するコードの価格を取得する（外部通信は最大30秒）。FMP失敗時は行ロック下で対象の存在・有効状態を再確認し、`last_checked_at`と`PRICE_FETCH_FAILED`だけ保存して次の対象へ進む。
5. 成功時はトランザクションを開始し、対象を`SELECT ... FOR UPDATE`でロックする。削除済み・停止済みなら保存・通知せずスキップする。
6. 取得価格、取得完了日時、最終確認日時を保存し、最高値・通知条件を判定する。必要な場合、ロックを保持したままLINEへ1回送信する（最大30秒）。
7. LINE成功時だけ通知済み率を更新する。LINE失敗は例外による一括ロールバックにせず、取得価格と日時、`NOTIFICATION_FAILED`をコミットし、通知済み率を保持する。次回はその時点の価格で再判定する。
8. 通知不要・最高値更新・通知成功の場合はエラーを`null`にする。DB失敗ではトランザクションをロールバックする。処理済み対象の変更は維持し、可能なら残りを処理する。
9. 全成功は終了0、設定不備・DB障害・1件以上の銘柄失敗は終了1。接続終了時にadvisory lockを解放する。

FMPへの登録時アクセスはWebプロセスから実行する。日次処理中に登録された対象は次回から処理する。取得時刻`latest_fetched_at`はアプリが有効価格の取得を完了した日時であり、市場の約定日時ではない。

## 障害・排他・制約

- DBの行ロック待機は最大60秒。待機超過は銘柄失敗、APIでは`503 RESOURCE_BUSY`として再試行を案内する。
- LINE呼び出し中の停止・削除は行ロックを待つ。ロック取得後に停止・削除が完了する。ブラウザは処理中ボタンを無効化する。
- 通知を受け付けた直後に通信が切れた場合、または受付後からDBコミットまでに停止した場合、次の実行で重複送信し得る。永続化した送信ジョブ・exactly-once保証は設けない。
- LINEの同一要求を実行内で即時再試行しない。次回の日次実行で最新価格を再判定する。24時間後の再判定では内容が変わり得るため、LINEの再試行キーによる永続的な重複排除は前提にしない。[LINEの受付・再試行仕様](https://developers.line.biz/en/docs/messaging-api/retrying-api-request/)を参照。
- 土日・祝日も実行し、取得できた値で判定する。同一価格による再通知は条件で抑制する。日中の最高値・一時的な急落、停止期間や停止した実行の履歴は補完しない。
- APIキー・LINEトークン・外部レスポンス本文・パスワード・Cookieをログへ出力しない。
