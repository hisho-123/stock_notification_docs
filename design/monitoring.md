# 通知・日次処理仕様

## 最高値・下落率・水準ごとの状態

最高値`H`は登録時に保存した価格と、その後の日次処理で鮮度確認を通過した価格の最大値。最終取得値を`P`とすると下落率は`(H-P)/H×100`。価格0・負数・NaN・Infinityは使用しない。判定は十進数の丸め前の値で行い、表示用の下落率だけ小数2桁に四捨五入する。

各ユーザーの銘柄・設定率`t`について、下落通知成功後から回復通知成功までを「回復待ち」とする。内部テーブル`asset_recovery_states`に下落通知時の最高値`B`を保存する。待ちがなければ下落通知の対象、待ちがあれば回復通知の対象となる。登録時は回復待ち0件。

`last_notified_threshold`（以下`L`）は、現在の最高値を基準に最後に成功した下落通知に含まれる最大率を表す表示用の値。通知の抑制・回復判定には使用しない。回復通知や設定変更では変更せず、最高値を更新した場合だけ`null`へ戻す。

## 下落・回復の判定と送信

鮮度確認を通過した価格について、次の順序で判定する。設定は所有者ごとの実行開始時のスナップショット、回復待ちは当該銘柄の処理開始時の状態を使う。

1. 回復待ちのうち、設定に含まれる各`t`について`P×100 > B×(100−t)`を満たすものを回復候補にする。基準価格`B×(100−t)/100`と同値では回復としない。
2. `P>H`なら最高値を`P`へ更新し、`L=null`にする。この実行の下落候補は0件。回復候補は更新前の待ちに保存された`B`で判定済みなので、最高値更新によって捨てない。`P=H`では最高値も`L`も変更しないが、回復条件は通常どおり判定する。
3. `P≤H`なら、設定のうち処理開始時に回復待ちがなく、`(H−P)×100 ≥ H×t`を満たす**全ての率**を下落候補にする。直前価格との交差は必須にせず、設定追加後や前回送信失敗後も最新価格で判定する。
4. 候補があれば、所有者の`line_following=true`なら銘柄につき1実行1通にまとめ、`users.line_user_id`へ送る。下落・回復の両方がある場合も1通内で区別する。各区分の率は昇順。同じ率は処理開始時の状態によって片方の候補にしかならず、回復した率の再下落判定は次回から行う。
5. LINEがHTTP 200で受け付けた場合だけ、下落候補の回復待ちを`B=今回のH`で作成し、回復候補の待ちを削除する。下落候補があれば`L`をその最大率に更新する。1通にまとめた全候補の状態更新を同一トランザクションで保存する。

回復待ちがある間は、同じ水準の下落通知を繰り返さない。回復通知成功後は再び下落・回復を繰り返し通知する。例としてH=100・t=10では、90で下落、90のままなら通知なし、90.0001で回復、次回90で再び下落となる。表示が10.00%でも丸め前の価格で判定する。

新高値で回復通知が失敗した場合も、最高値・価格・日時は更新し、回復待ちと当時の`B`を保持する。現在の最高値で回復価格を再計算すると、通知していた水準が変わるためである。翌日は保存した`B`と最新価格で再判定し、最新価格が回復条件を満たさなければ過去の回復は送らない。待ちは回復通知成功または設定削除まで保持する。

| 送信結果 | 状態・エラー |
| --- | --- |
| HTTP 200で受付 | 全候補の待ちを作成・削除し、下落があればLを更新。エラーをnullにする |
| 送信失敗 | 待ちを全て保持。取得価格・最高値・日時とNOTIFICATION_FAILEDを保存。新高値ならL=null、それ以外のLは保持 |
| 候補なし | 待ちを保持し、価格・最高値・日時を保存。エラーをnullにする |
| 所有者がLINEをブロック中 | 送信・待ちの作成削除なし。新高値とL=nullは通常どおり保存し、抑止自体はエラーにしない |

回復通知専用の有効・無効設定は設けない。既存の監視状態と通知率を使用する。関連実装に必要な変更は[関連実装への影響](implementation-impact.md)を参照。

## 通知設定の変更

設定保存時に、本人の銘柄に限り、削除された率の回復待ちを停止中の対象も含めて取り消す。他ユーザーの設定・回復待ちは変更しない。設定更新と待ちの削除は同一トランザクションとし、どちらかのDB処理が失敗した場合は両方を戻す。最高値・価格・Lは変更せず、送信も行わない。

維持した率の待ちとBは保持する。追加・再追加した率は待ちなしで開始し、次の監視で既に下落条件を満たしていれば通知する。削除した待ちは再追加しても復元しない。日次判定も、その実行の設定に含まれる率だけを候補にする。

監視実行中の設定変更は次回から適用する。同時実行との排他制御は設けず、保存完了後の旧設定による送信や待ちの再作成を保証して抑止しない。削除・再追加の順序を確実に反映させるため、監視中の設定変更も運用で避ける。

## 価格データの鮮度・自動停止

FMP Quote応答の一致するレコードから`price`と`timestamp`を取得する。`timestamp`はUNIX秒の整数としてUTC日時に変換する。欠落・null・整数以外・日時に変換できない値は価格取得失敗とする。価格が有限かつ正でもtimestampの検証は省略しない。

アプリの取得完了時刻からFMPのtimestampを引いた経過時間が240時間（864,000秒）以上なら古いデータとする。10日ちょうどを含み、日付単位の丸めや土日・祝日の除外は行わない。10日未満の遅延は許容する。

日次処理で古いデータを検知した場合、下落・回復判定と最高値更新を行わない。保存済み価格・最高値・`latest_fetched_at`・L・回復待ちとBを保持し、`last_checked_at`を取得完了時刻へ更新する。通知率とは独立して、銘柄につき1実行1回だけ停滞通知を試みる。

| 停滞通知の結果 | 保存する状態と次回の扱い |
| --- | --- |
| LINEがHTTP 200で受付 | `monitoring_enabled=false`、`last_error_code=PRICE_DATA_STALE`を保存。手動再開まで日次処理から除外する |
| LINE送信失敗 | `monitoring_enabled=true`を維持し、`last_error_code=NOTIFICATION_FAILED`を保存。同じ実行内では再送せず、翌日再取得して鮮度を再判定する |
| 所有者がブロック中 | 送信せず、`monitoring_enabled=true`・`last_error_code=PRICE_DATA_STALE`を保存。自動停止せず、翌日も鮮度を確認する |

翌日に鮮度確認を通過すれば通常の下落・回復判定へ戻る。まだ古ければ停滞通知を1回試み、受付成功時に停止する。停止中は価格取得しない。手動再開時も即時取得・通知せず、保存した回復待ちとBで次の監視を行う。

登録時に古い価格が返った場合は、その価格を初期最高値・最終取得値として警告付きの停止状態で登録する。`last_error_code=PRICE_DATA_STALE`、L=null・回復待ち0件とし、取得日時・最終確認日時は実際の取得完了時刻を保存する。登録時のLINE通知は行わない。FMPのtimestamp専用のDB列・API項目は設けない。

## ユーザー別の処理・ブロック中の扱い

同じ銘柄でもユーザーごとの登録行・最高値・L・回復待ちとBを使用し、別ユーザーの状態を流用しない。価格取得も登録行ごとに行い、ユーザー間の取得共通化・一括通知は初期版では設けない。送信先をクライアント入力や固定の環境変数から取得しない。

ブロック中も`monitoring_enabled=true`の対象は通常どおり取得・更新する。新高値では通常どおりLをnullへ戻す。それ以外はLを保持し、送っていない通知を成功扱いせず、回復待ちの作成・削除を行わない。新高値でも既存の回復待ちとBは保持する。正常な価格処理なら既存エラーを解消し、通知抑止だけを`NOTIFICATION_FAILED`にしない。古い価格は上表に従い、価格取得失敗は通常の`PRICE_FETCH_FAILED`とする。ブロック抑止だけなら終了0、古い価格検知はブロック中でも終了1。

ブロック解除時に即時通知・即時取得・Lや回復待ちのリセットは行わない。次の日次実行でその時点の価格と保持した状態から判定し、過去に検知した下落・回復・停滞通知を繰り越さない。成功済みの下落に対応する回復待ちは保持し、そのBと最新価格で判定する。送信直前に所有者の友だち状態を読み直すが、Webhook処理との排他制御はせず、その確認後の競合による送信は許容する。

## 通知例

以下は仮の価格。下落通知には今回新たに到達した全水準を含める。

```text
株・指数の下落通知
銘柄: S&P 500 (^GSPC)
下落率: 27.00%
到達閾値: 10%, 15%, 20%, 25%
監視開始後の最高値: 6000
最終取得値: 4380
取得日時: 2026-11-03 07:00 JST
```

回復通知には回復した率ごとの基準最高値・基準価格を含め、「基準価格を超えた」ことを伝える。現在の最高値とBが異なる場合も区別できるよう、Bを省略しない。

```text
株・指数の回復通知
銘柄: S&P 500 (^GSPC)
下落率: 19.00%
回復した水準:
20%: 基準最高値6000 / 基準価格4800を超えました
25%: 基準最高値6000 / 基準価格4500を超えました
監視開始後の最高値: 6000
最終取得値: 4860
取得日時: 2026-11-04 07:00 JST
```

下落・回復が同時の場合は表題を「株・指数の下落・回復通知」とし、「下落：到達閾値」「回復：回復した水準」の区分を設ける。共通の銘柄・現在の下落率・最高値・価格・取得日時は1回だけ表示する。

停滞通知は銘柄名・コード・FMPデータ日時・検知日時・自動停止と手動再開の案内を含める。

```text
価格データの停滞通知
銘柄: Apple Inc. (AAPL)
価格データが10日以上前です。
FMPデータ日時: 2026-10-24 07:00 JST
検知日時: 2026-11-03 07:00 JST
監視を自動停止します。データ提供状況を確認し、必要に応じて手動で再開してください。
```

価格は通貨換算せず、対象の提供価格の単位で扱う。全ての通知はLINEのHTTP 200で受付成功とし、配信・既読は保証しない。

## 判定の具体例

特記しない場合は設定`[10,15,20,25,30]`、H=100。`W={10,20}`はB=100で10%・20%が回復待ちであることを示す。各行は独立し、「連続」行だけ順に実行する。価格は古いデータの例以外は鮮度確認を通過し、送信は失敗と記載した場合以外は成功する。

| 条件 | 結果 |
| --- | --- |
| Wなし、90.0001と90 | 前者は下落通知なし、後者は10%下落を1通。W={10}、L=10 |
| W={10}、90→90.0001→90（連続） | 同値では通知なし、90.0001で回復・Wなし、次の90で再下落・W={10} |
| Wなし、73 | 10・15・20・25%下落を1通、W={10,15,20,25}、L=25 |
| 設定[10,20,30]、Wなし、65→75→85→95（連続） | 65で全3率の下落を1通。75で30%、85で20%、95で10%回復を各1通 |
| 設定[10,20,30]、W={10,20,30}、95 | 全3率の回復を1通、Wなし。Lは変更しない |
| W={10,15,20}、L=20、95→80→100（連続） | 95で全3率回復、80で全3率再下落、100で全3率回復。H=100・L=20を保持 |
| W={10,15,20}、110→99（連続） | 110で旧B=100の3率回復、H=110・L=null。99で10%下落、B=110・L=10 |
| W={10}、L=10、110で回復失敗→翌日95（連続） | 失敗時H=110・L=null、B=100の待ち保持。95は旧基準90を超えるため10%回復。新H基準の10%下落は同じ実行では送らず、翌日も95なら新たに下落通知 |
| W={10}、95で回復失敗→翌日85（連続） | 翌日に10%回復は送らず待ち保持。15%の新たな下落だけを通知、W={10,15}。過去の回復は繰り越さない |
| W={20}、設定[10,20]へ10%追加、P=85 | 10%下落と20%回復を1通。成功時W={10}、L=10 |
| W={10,15,20}、設定を[5,15,25]へ変更、80→75（連続） | 保存時10・20%待ち取消、15%維持。80で5%下落、75で25%下落。削除した20%の回復は送らない |
| 停止中に10%削除→再追加 | 保存時に待ち取消、再追加で復元なし。再開後90なら10%下落から開始 |
| 停止中の価格70、再開後85、Wなし | 停止中の70は扱わず、10・15%下落を1通 |
| Wなし、75で下落失敗→翌日95（連続） | 待ち作成なし、翌日は下落も回復も通知なし、L=null・エラー解消 |
| Wなし、75で下落失敗→翌日75（連続） | 翌日の価格で10・15・20・25%下落を1通。成功時だけ待ち作成・L=25 |
| 分割で100→50→40（連続） | 分割補正せず50で全設定率の下落を1通、L=30。40で追加通知なし |
| 240時間前の価格75、停滞通知成功 | 下落・回復なし。価格・H・取得日時・L・WとB保持、警告付き自動停止 |
| 削除後に80で再登録 | 新ID、H=80、L=null、回復待ち0件 |

## 実行手順

外部スケジューラは毎日07:00（`Asia/Tokyo`）に`stock-notification monitor`を1回起動する。API経由の監視開始機能は設けない。

1. 必須設定とDB接続を確認する。監視全体の排他ロックは取得しない。
2. 全ユーザーの通知閾値を実行開始時に1回読み、ユーザー別のスナップショットを作る。次項の対象一覧と同じ短い読み取りトランザクションのスナップショットを使い、途中の登録・変更は次回から適用する。設定欠落は当該ユーザーの失敗として記録してスキップし、他ユーザーは継続する。
3. 有効な対象のID・コード・所有者login_idをID順で読み、順番に処理する。開始時に読み出したユーザー・対象だけを処理し、実行中の新規登録は次回から。ユーザー・対象0件は正常終了0。
4. FMPから一致するコードの価格とtimestampを取得・検証する（外部通信は最大30秒）。FMP失敗・timestamp不正時は対象の存在・所有者・有効状態を再確認し、処理対象ならlast_checked_atとPRICE_FETCH_FAILEDを保存して次へ進む。価格・H・L・回復待ちは保持する。
5. 成功時はトランザクションを開始し、明示的な行ロックなしで対象の存在・所有者・有効状態と当該銘柄の回復待ちを読む。所有者のLINEユーザーID・友だち状態もDBから取得する。削除済み・停止済みなら保存・通知せずスキップする。この確認後の競合までは防がない。
6. 古いデータなら所有者への停滞通知だけを1回試み（ブロック中は抑止）、結果をコミットする。下落・回復候補は作らない。
7. 鮮度確認を通過した場合、前述の順序で回復候補・最高値更新・下落候補を決め、所有者の閾値を使って必要なら所有者のLINEへ1通送信する。LINE通信も最大30秒。送信直前に所有者の友だち状態を読み直し、ブロック中は送信と待ちの作成削除を抑止する。
8. 取得価格・日時・最高値更新は送信失敗時も保存する。受付成功時だけ候補の待ちを作成・削除し、下落があればLを更新する。失敗時はNOTIFICATION_FAILEDを保存し、即時再送せず翌日の最新価格で再判定する。
9. 通知不要・受付成功・ブロック抑止ならエラーをnullにする。DB失敗では対象と待ちの変更をロールバック。接続を維持できれば残りを処理し、接続断なら再接続せず終了1。処理済み対象の変更は維持する。
10. 全成功は終了0、設定不備・DB障害・1件以上の銘柄失敗・古いデータ検知は終了1。停滞通知成功による自動停止も終了1。

FMPへの登録時アクセスはWebプロセスから行う。latest_fetched_atは保存対象価格の取得完了日時で、市場の約定日時やFMPのtimestampではない。日次処理では鮮度確認を通過した場合だけ更新し、警告付き新規登録では古い価格でも取得完了日時を保存する。

## 障害・運用上の制約

- 監視全体のadvisory lockと明示的な行ロックによる排他制御は設けない。トランザクション・ユニーク制約・外部キーは維持する。監視の重複起動、監視中の設定変更・停止・再開・削除は運用で避ける。
- 同時実行時の二重通知、価格・待ちの更新順序、設定削除・停止・削除完了後の送信抑止は保証しない。実行中の停止→再開は同じ実行で通知され得る。
- 株式分割は自動検知・価格補正しない。誤った下落・回復や通知抑制が起こり得る。状態を作り直す場合は削除・再登録する。
- 下落・回復の失敗を永続的な再送待ちジョブにしない。回復待ちは成功した下落に対応する状態であり、過去に検知した回復の送信予約ではない。最新価格で条件を満たさなければ通知せず、未通知の急落・一時的な回復が残ることを許容する。
- LINE受付直後の通信断、受付後のDB保存失敗・プロセス停止では翌日重複送信し得る。まとめた通知の全候補が重複する可能性がある。永続送信ジョブ・exactly-once保証は設けない。
- LINE要求を実行内で即時再試行しない。翌日は内容が変わり得るため、再試行キーによる永続的な重複排除は前提にしない。[LINEの受付・再試行仕様](https://developers.line.biz/en/docs/messaging-api/retrying-api-request/)を参照。
- 土日・祝日も実行する。同一価格で判定と送信に成功した後は、設定・最高値・待ちが同じなら不要な再通知はしない。日中の値動きや停止期間の履歴は補完しない。
- 価格取得・全ての待ちの参照更新・設定削除を所有者ごとに分離する。ブロック解除時の即時取得・通知はせず、次回の最新価格で判定する。抑止中に新高値となってもBを保持する。
- APIキー・LINEトークン・外部レスポンス本文・パスワード・Cookieをログへ出力しない。
