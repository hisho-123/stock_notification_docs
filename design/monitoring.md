# 通知・日次処理仕様

## 最高値・下落率・通知条件

最高値`H`は登録時に保存した価格と、その後の日次処理で鮮度確認を通過した価格の最大値。最終取得値を`P`とすると下落率は`(H-P)/H×100`。`P>H`なら`H=P`へ更新し、最終通知済み率`L`を`null`に戻す。この実行では下落通知しない。

`P≤H`の場合、その銘柄の所有者の通知設定のうち`(H-P)×100 ≥ H×閾値`を満たす最大値を到達閾値`T`とする。到達値がなければ通知しない。`T>L`（`L=null`は0と扱う）かつ所有者の`line_following=true`の場合にだけ、`users.line_user_id`へ送信する。通知判定は十進数の丸め前の値で行い、表示用の下落率だけ小数2桁に四捨五入する。

価格0・負数・NaN・Infinityは使用しない。最高値と同じ価格に戻っても通知済み率はリセットしない。30%通知後にさらに下落しても、設定により大きい閾値がなければ追加通知しない。

## 価格データの鮮度・自動停止

FMP Quote応答の一致するレコードから`price`と`timestamp`を取得する。`timestamp`はUNIX秒の整数としてUTC日時に変換する。欠落・null・整数以外・日時に変換できない値は不正レスポンスとして価格取得失敗とする。価格が有限かつ正でも、timestampの検証は省略しない。

アプリの取得完了時刻からFMPのtimestampを引いた経過時間が240時間（864,000秒）以上なら、10日以上前の古いデータと判定する。10日ちょうどを含み、日付単位の丸めや土日・祝日の除外は行わない。10日未満の遅延は許容する。

日次処理で古いデータを検知した場合、下落判定と最高値更新を行わない。保存済みの価格・最高値・`latest_fetched_at`・通知済み率を保持し、`last_checked_at`を取得完了時刻へ更新する。下落率の通知設定とは独立して、銘柄につき1実行1回だけ停滞通知をLINEへ送る。

| 停滞通知の結果 | 保存する状態と次回の扱い |
| --- | --- |
| LINEがHTTP 200で受付 | `monitoring_enabled=false`、`last_error_code=PRICE_DATA_STALE`を保存。手動再開まで日次処理から除外する |
| LINE送信失敗 | `monitoring_enabled=true`を維持し、`last_error_code=NOTIFICATION_FAILED`を保存。同じ実行内では再送せず、翌日再取得して鮮度を再判定する |
| 所有者がブロック中 | 送信せず、`monitoring_enabled=true`・`last_error_code=PRICE_DATA_STALE`を保存。自動停止せず、翌日も鮮度を確認する |

翌日に鮮度確認を通過すれば通常の下落判定へ戻る。まだ古ければ停滞通知を1回試み、受付成功時に停止する。自動停止後の自動再開・停止中の価格取得は行わない。手動再開時も即時取得・通知はせず、次に対象として処理される際に再判定する。

登録時に古い価格が返った場合は、その価格を初期最高値・最終取得値として警告付きの停止状態で登録する。`last_error_code=PRICE_DATA_STALE`、未通知とし、取得日時・最終確認日時は実際の取得完了時刻を保存する。登録時のLINE通知は行わない。FMPのtimestamp専用のDB列・API項目は設けない。

## ユーザー別の処理・ブロック中の扱い

同じ銘柄でもユーザーごとの登録行・最高値・通知済み率を使用し、別ユーザーの状態を流用しない。価格取得も登録行ごとに行い、ユーザー間の取得共通化・一括通知は初期版では設けない。送信先をクライアント入力や固定の環境変数から取得しない。

ブロック中も`monitoring_enabled=true`の対象は通常どおり取得・更新する。新高値では通常どおり通知済み率をnullへ戻す。それ以外は通知済み率を保持し、送っていない通知を成功扱いしない。正常な価格処理なら既存エラーを解消し、通知抑止だけを`NOTIFICATION_FAILED`にしない。古い価格は上表に従い、価格取得失敗は通常の`PRICE_FETCH_FAILED`とする。ブロック抑止だけなら終了0、古い価格検知はブロック中でも終了1。

ブロック解除時に即時通知・即時取得・通知済み率のリセットは行わない。次の日次実行でその時点の価格と保持した状態から判定し、過去の下落・停滞通知を繰り越さない。送信直前に所有者の友だち状態を読み直すが、Webhook処理との排他制御はせず、その確認後の競合による送信は許容する。

## 通知例

以下は仕様説明用の仮の価格。下落通知は次の項目を含める。

```text
株・指数の下落通知
銘柄: S&P 500 (^GSPC)
下落率: 27.00%
到達閾値: 25%
監視開始後の最高値: 6000
最終取得値: 4380
取得日時: 2026-10-08 07:00 JST
```

停滞通知は銘柄名・コード・FMPデータ日時・検知日時・自動停止と手動再開の案内を含める。

```text
価格データの停滞通知
銘柄: Apple Inc. (AAPL)
価格データが10日以上前です。
FMPデータ日時: 2026-09-28 07:00 JST
検知日時: 2026-10-08 07:00 JST
監視を自動停止します。データ提供状況を確認し、必要に応じて手動で再開してください。
```

価格は通貨換算せず、対象の提供価格の単位で扱う。どちらの通知もLINEがHTTP 200で受け付けた場合を送信成功とする。ユーザーへの配信・既読は保証しない。

## 判定の具体例

初期設定は`[10,15,20,25,30]`、最高値100とする。各行は独立した例（「連続」行だけ順に実行）。価格は、古いデータの例以外は鮮度確認を通過しているものとする。

| 条件 | 結果 |
| --- | --- |
| 未通知、90.0001 | 下落率表示は10.00%でも丸め前は10%未満。通知しない |
| 未通知、90 | 10%を1通通知、通知済み率10 |
| 未通知、73 | 27%下落。25%を1通通知、通知済み率25 |
| 通知済み20、95→80（連続） | 回復後に再下落しても20%で再通知しない |
| 通知済み20、100 | 最高値と同値なので通知済み20を保持 |
| 通知済み20、110→99（連続） | 110で最高値更新・未通知に戻る。99で10%を通知 |
| 通知済み30、60 | 設定上の最大30%を超えても再通知しない |
| 通知済み20、設定を[5,15,25]へ変更、価格80 | 15%到達だが通知済み20以下。通知しない |
| 同じ設定変更後、価格75 | 25%を通知 |
| 停止中に価格70、再開後の日次取得価格85、通知済みnull | 停止中の70は扱わず、15%を通知 |
| 削除後に価格80で再登録 | 最高値80、未通知、下落率0.00%で開始 |
| 未通知、75で下落通知失敗→翌日95（連続） | 失敗直後の再送なし。翌日は通知不要、未通知のまま、エラー解消。過去の25%下落は通知しない |
| 未通知、75で下落通知失敗→翌日75（連続） | 翌日の最新価格で25%到達を判定し、1通送信する |
| 1株→2株の分割で100→50→40（連続） | 分割を補正せず、50で50%下落として30%通知。最高値100・通知済み30を保持し、40では追加通知しない |
| 取得完了時刻より240時間前の価格75、停滞通知成功 | 下落通知なし。保存済み価格・最高値・取得日時・通知済み率を保持し、警告付きで自動停止 |
| 対象読み出し後、価格取得中に停止→再開 | 再確認時に有効なら同じ実行で処理・通知され得る。監視中の操作は運用で避ける |

## 実行手順

外部スケジューラは毎日07:00（`Asia/Tokyo`）に`stock-notification monitor`を1回起動する。API経由の監視開始機能は設けない。

1. 必須設定とDB接続を確認する。監視全体の排他ロックは取得しない。
2. 全ユーザーの通知閾値を実行開始時に1回読み、ユーザー別のスナップショットを作る。次項の対象一覧と同じ短い読み取りトランザクションのスナップショットを使い、途中の登録・変更は次回から適用する。設定欠落は当該ユーザーの失敗として記録してスキップし、他ユーザーは継続する。
3. 有効な対象のID・コード・所有者login_idをID順で読み、順番に処理する。開始時に読み出したユーザー・対象だけを処理し、実行中の新規登録は次回から。ユーザー・対象0件は正常終了0。
4. FMPから一致するコードの価格とtimestampを取得・検証する（外部通信は最大30秒）。FMP失敗・timestamp不正時は対象の存在・有効状態を再確認し、処理対象なら`last_checked_at`と`PRICE_FETCH_FAILED`を保存して次の対象へ進む。
5. 成功時はトランザクションを開始し、明示的な行ロックなしで対象の存在・所有者・有効状態を再確認する。削除済み・停止済みなら保存・通知せずスキップする。所有者のLINEユーザーID・友だち状態をDBから取得する。この確認後の競合までは防がない。
6. 古いデータなら「価格データの鮮度・自動停止」に従って所有者へ停滞通知を1回試み、結果をコミットする。ブロック中は送信を抑止する。価格・最高値・取得日時・通知済み率は更新せず、この銘柄の下落判定は行わない。
7. 鮮度確認を通過した価格は、取得価格・取得完了日時・最終確認日時を保存し、所有者の閾値で最高値・通知条件を判定する。必要かつブロック中でなければ、所有者のLINEへ下落通知を1回送信する（停滞通知も含め外部通信は最大30秒）。
8. 下落通知成功時だけ通知済み率を更新する。下落通知失敗は例外による一括ロールバックにせず、取得価格と日時、`NOTIFICATION_FAILED`をコミットし、通知済み率を保持する。送信失敗後は再送などの追加処理を行わず、翌日の日次実行でその時点の最新価格から通常の通知条件を再判定する。
9. 鮮度確認を通過し、通知不要・最高値更新・下落通知成功の場合はエラーを`null`にする。DB失敗では対象のトランザクションをロールバックする。接続を維持できれば残りを処理するが、接続断では再接続せず終了1。処理済み対象の変更は維持する。
10. 全成功は終了0、設定不備・DB障害・1件以上の銘柄失敗・古いデータ検知は終了1。停滞通知が成功して自動停止できた場合も終了1とする。

FMPへの登録時アクセスはWebプロセスから実行する。日次処理中に登録された対象は次回から処理する。`latest_fetched_at`は保存対象の価格をアプリが取得完了した日時で、市場の約定日時やFMPのtimestampではない。日次処理では鮮度確認を通過した場合だけ更新し、警告付きの新規登録では古い価格でも取得完了日時を保存する。

## 障害・運用上の制約

- 複数ユーザー対応後も、監視全体のadvisory lockと明示的な行ロックによる排他制御は設けない。トランザクション・ユニーク制約などのDB制約は維持する。監視の重複起動、監視中の停止・再開・削除は運用で避け、全利用者に制約を案内する。
- 同時実行時の二重通知、価格の更新順序、停止・削除完了後の送信抑止は保証しない。実行中の停止→再開を記録して当該実行を無効化する仕組みも設けず、同じ実行で通知され得ることを許容する。
- 株式分割は自動検知・価格補正しない。分割前の最高値も保持し、誤った下落通知や、その後の通知抑制が起こり得る。この制約を利用者に案内する。最高値・通知済み状態を作り直す場合は本人が削除・再登録する。
- 下落通知の失敗を永続的な再送待ちとして保持しない。回復後に過去の下落を届ける必要性は低いと判断し、検知済みの急落が未通知のままになることを許容する。再送待ちジョブ・過去の急落の繰越は設けない。
- 通知を受け付けた直後に通信が切れた場合、または受付後からDBコミットまでに停止した場合、翌日の実行で重複送信し得る。停滞通知受付後に自動停止の保存が失敗した場合も同様。永続化した送信ジョブ・exactly-once保証は設けない。
- LINEの同一要求を実行内で即時再試行しない。翌日の日次実行で最新価格・timestampを再判定する。24時間後には内容が変わり得るため、LINEの再試行キーによる永続的な重複排除は前提にしない。[LINEの受付・再試行仕様](https://developers.line.biz/en/docs/messaging-api/retrying-api-request/)を参照。
- 土日・祝日も実行する。鮮度確認を通過した同一価格による再通知は下落条件で抑制する。日中の最高値・一時的な急落、停止期間や停止した実行の履歴は補完しない。
- APIキー・LINEトークン・外部レスポンス本文・パスワード・Cookieをログへ出力しない。
