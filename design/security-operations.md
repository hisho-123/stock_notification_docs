# 認証・運用仕様

## 認証とCookie

ユーザーごとの`login_id`・bcryptパスワードハッシュ（cost 12以上）を`users`テーブルで管理する。IDは1〜100文字、パスワードはUTF-8で8〜72バイト。前後空白・大小文字を含めIDは完全一致、パスワードも空白を除去しない。未知のID・パスワード不一致は同じ`401 INVALID_CREDENTIALS`を返し、未知のIDでもダミーハッシュ照合を行う。平文パスワードを保存・ログ出力しない。別の`user_id`や固定管理者は設けない。

ログイン・登録成功時は暗号学的乱数でセッションとCSRFトークンを生成し、`login_id`に紐付けてDBに保存する。発行済みのCookieがあればそのセッションだけを失効して置き換える。セッションは発行から24時間の固定期限で延長しない。他ブラウザ・他ユーザーのセッションは維持する。

| Cookie | 属性・用途 |
| --- | --- |
| `__Host-stock_session` | Secure、HttpOnly、SameSite=Strict、Path=/、Domainなし、Max-Age=86400。セッショントークン |
| `__Host-stock_csrf` | Secure、HttpOnly、SameSite=Strict、Path=/、Domainなし、Max-Age=86400。CSRFトークン。JSはCookieを読まずセッションAPIの応答を使う |

HTTPSの同一オリジンでReactとGo APIを提供する。CORSで他オリジンを許可しない。認証CookieやCSRFトークンをlocalStorage・URL・ログに保存しない。

`GET /api/v1/auth/session`はセッションが有効なら`login_id`、期限、Cookieに対応する`csrf_token`だけを返す。LINEユーザーIDやパスワードハッシュは返さない。CSRF Cookieもハッシュと照合する。不備・期限切れ・ユーザー不在は`401 UNAUTHENTICATED`。ログアウトでは該当DB行と両Cookieを削除する。Cookieだけを消した状態の旧セッションも期限で失効する。LINEのブロックはWebログインを失効させない。

## CSRF・アクセス制御

- Webhookを除くPOST/PATCH/PUT/DELETEは`Origin`を`PUBLIC_ORIGIN`と完全一致で確認する。欠落・不一致は`403 CSRF_FAILED`。外部サイトからのログイン・登録要求も拒否する。
- 公開APIのログイン・登録・登録トークン確認・Webhook以外は認証を必須とし、変更系はさらに`X-CSRF-Token`を要求する。セッションに紐付くハッシュと定数時間比較する。トークンはログイン・登録・セッション確認APIから取得し、Reactのメモリで保持する。
- ログイン・登録・登録トークン確認はCSRFトークンを要求せず、同一オリジン確認とJSON Content-Typeを必須とする。フォームPOSTでは受け付けない。
- WebhookだけはOrigin・Cookie・CSRFを要求せず、`X-Line-Signature`を検証する。署名不正なら本文を業務処理しない。詳細は[登録・LINE連携](registration.md)を参照。
- 保護APIではセッションの`login_id`をDB検索・更新・削除の条件に必ず含める。検索・件数にも所有者条件を適用し、他ユーザーの銘柄への操作は404。同じ銘柄の別ユーザー登録は許可する。
- ログイン・セッションAPIの応答は`Cache-Control: no-store`。その他APIも管理データのため`no-store`とする。
- 保護APIの認証失敗時は401を返し、Reactは画面内データを破棄してログインへ遷移する。ログアウト・ユーザー切替でも一覧・設定・未保存入力・CSRFを破棄し、旧要求の遅延応答を新ユーザーへ反映しない。変更操作をログイン後に自動再送しない。

## ログイン試行制限

接続元IPごとの認証失敗を直近15分で数え、5回失敗後のログイン要求は`429 TOO_MANY_ATTEMPTS`と`Retry-After`（秒）で拒否する。最も古い失敗が15分の窓から外れれば再試行可能。成功したIPの失敗履歴はクリアする。プロセスメモリで管理するためWebプロセスは1台・1プロセスを前提とし、再起動時はカウンタをリセットする。

登録・登録トークン確認にもIP別に直近15分・30要求の上限を設け、超過は429・Retry-Afterとする。ログインとは別カウンタで、成功でもこの登録用カウンタはクリアしない。LINEの再発行コマンドはLINEユーザーID別に15分・5回までとし、超過時はURLを更新せず待機を返信する。Webhook全体をブラウザのIP制限には含めない。

接続元IPは信頼するプロキシの設定を経由した値だけを採用し、任意の`X-Forwarded-For`を信用しない。

## 運用設定

| 設定 | 内容 |
| --- | --- |
| `DATABASE_URL` | PostgreSQL接続文字列。パスワードを含むので秘密として管理 |
| `FMP_API_KEY` | FMP APIキー |
| `LINE_TOKEN` | LINE Messaging APIチャネルアクセストークン |
| `LINE_CHANNEL_SECRET` | Webhook署名検証用のチャネルシークレット |
| `PUBLIC_ORIGIN` | 公開URLのオリジン。例：`https://stock.example.com`。パス・末尾スラッシュなし |
| `HTTP_ADDR` | Goの待受アドレス。既定`127.0.0.1:8080` |

WebにはDB・FMP・LINE_TOKEN・LINE_CHANNEL_SECRET・PUBLIC_ORIGIN、監視コマンドにはDB・FMP・LINE_TOKENが必要。必須設定不足は起動・実行前に失敗させる。固定管理者の`ADMIN_ID`・`ADMIN_PASSWORD_HASH`、固定通知先の`LINE_USER_ID`は廃止する。チャネルシークレット・アクセストークンは同じ公式アカウントのチャネルに統一する。

LINE Developers ConsoleでWebhook URLを`PUBLIC_ORIGIN/api/v1/webhooks/line`に設定し、Webhookと再配信を有効化する。署名付き空イベントの検証、follow、unfollow、テキスト「登録」を受信できることを確認する。URLが届かない場合の「登録」送信を公式アカウントの案内に含め、二重案内を避けるよう定型あいさつ・自動応答を調整する。契約に必要な権限と全ユーザー分の送信枠を用意する。

## 定期実行・デプロイ

- 外部スケジューラ側のタイムゾーンを`Asia/Tokyo`に設定し、毎日07:00に`stock-notification monitor`を起動する。UTC指定なら毎日22:00 UTCが翌日の07:00 JSTに相当する。
- 監視全体のadvisory lock・明示的な行ロックによる排他制御は設けない。スケジューラを重複設定せず、手動実行や停止・再開・削除の前に監視コマンドの終了を確認する。複数ユーザーにも監視中の操作を避ける制約を案内し、同時実行時の通知・更新の整合性は保証しない。登録の二重消費防止とは区別する。
- 監視終了0/1と銘柄単位の処理結果を記録する。失敗・未実行は運用側で検知し、必要時に同じコマンドを手動実行する。停止した実行を自動で過去に遡って再生しない。古いデータの検知は停滞通知成功・自動停止時も終了1。自動停止後はデータ提供状況を確認して必要に応じて手動再開する。停滞通知失敗時は監視中を維持し、翌日の日次処理で再判定する。
- Webのリクエストタイムアウトは90秒、プロキシも90秒以上にする。外部APIの通信は30秒を上限とする。APIの中断時にも既に完了した登録・停止などは反映され得るので、再試行前に一覧を取得する。
- 日次処理中にDB接続が切れた場合は再接続して残処理を継続せず終了1。接続を維持できる対象単位の失敗はロールバックして他対象を続行する。処理済み対象の変更は維持する。
- デプロイ前に新スキーマで開発DBを再作成し、秘密情報・Webhookを設定して、外部APIを模擬した受け入れ検証を通す。旧DB・旧APIとの互換運用は行わない。稼働後は友だち追加・ユーザー登録・認証・銘柄登録、日次コマンドの終了状態を確認する。
- 期限切れセッションと期限切れ・使用済み・失効済みの登録トークンは毎日の監視開始時とWeb起動時に削除する。未掃除でも期限・使用状態を必ず確認する。Webhook履歴は削除しない。
- DBバックアップと復元手順を用意する。DBを復元したらセッションを全削除し、未使用登録トークンを失効する。通知済み状態・友だち状態もバックアップ時点へ戻るため、重複通知や実際のブロック状態との差が起こり得る。

ログは実行ID、監視対象ID、WebhookイベントID、返信結果、内部エラーコード、終了時刻を記録する。ログイン入力、LINEユーザーID、登録URL・トークン、replyToken、Cookie、CSRF、接続文字列、外部API URLのキー付きクエリやレスポンス本文は記録しない。登録画面はno-store・no-referrerとし、URLのフラグメントを外部解析に送らない。Webhook返信のpending残存・failedと日次処理のユーザー別失敗を運用で確認する。
