# 認証・運用仕様

## 認証とCookie

管理者1人のIDとbcryptパスワードハッシュ（cost 12以上）をサーバー設定で管理する。パスワード平文を保存・ログ出力しない。ID・パスワードが一致しなければ同じ`401 INVALID_CREDENTIALS`を返す。IDは完全一致、パスワードの空白は除去しない。

ログイン成功時は暗号学的乱数でセッションとCSRFトークンを生成し、セッションをDBに保存する。発行済みのCookieがあればそのセッションを失効して置き換える。セッションは発行から24時間の固定期限で延長しない。

| Cookie | 属性・用途 |
| --- | --- |
| `__Host-stock_session` | Secure、HttpOnly、SameSite=Strict、Path=/、Domainなし、Max-Age=86400。セッショントークン |
| `__Host-stock_csrf` | Secure、HttpOnly、SameSite=Strict、Path=/、Domainなし、Max-Age=86400。CSRFトークン。JSはCookieを読まずセッションAPIの応答を使う |

HTTPSの同一オリジンでReactとGo APIを提供する。CORSで他オリジンを許可しない。認証CookieやCSRFトークンをlocalStorage・URL・ログに保存しない。

`GET /api/v1/auth/session`はセッションが有効なら管理者ID、期限、Cookieに対応する`csrf_token`を返す。CSRF Cookieもハッシュと照合する。不備・期限切れは`401 UNAUTHENTICATED`。ログアウトではDB行と両Cookieを削除する。Cookieだけを消した状態の旧セッションも期限で失効する。

## CSRF・アクセス制御

- 全てのPOST/PATCH/PUT/DELETEは`Origin`を`PUBLIC_ORIGIN`と完全一致で確認する。欠落・不一致は`403 CSRF_FAILED`。外部サイトからのログイン要求も拒否する。
- ログイン以外の変更系APIは認証と`X-CSRF-Token`ヘッダーを必須とする。セッションに紐付くハッシュと定数時間比較する。トークンはログイン・セッション確認APIから取得し、Reactのメモリで保持する。
- ログインAPIは認証前なのでCSRFトークンを要求せず、同一オリジン確認とJSON Content-Typeを必須とする。フォームPOSTでは受け付けない。
- ログイン・セッションAPIの応答は`Cache-Control: no-store`。その他APIも管理データのため`no-store`とする。
- APIの認証失敗時は401を返し、Reactは画面内データを破棄してログインへ遷移する。変更操作をログイン後に自動再送しない。

## ログイン試行制限

接続元IPごとの認証失敗を直近15分で数え、5回失敗後のログイン要求は`429 TOO_MANY_ATTEMPTS`と`Retry-After`（秒）で拒否する。最も古い失敗が15分の窓から外れれば再試行可能。成功したIPの失敗履歴はクリアする。プロセスメモリで管理するためWebプロセスは1台・1プロセスを前提とし、再起動時はカウンタをリセットする。

接続元IPは信頼するプロキシの設定を経由した値だけを採用し、任意の`X-Forwarded-For`を信用しない。管理者の設定変更は運用側で行い、全セッションを削除してWebプロセスを再起動する。

## 運用設定

| 設定 | 内容 |
| --- | --- |
| `DATABASE_URL` | PostgreSQL接続文字列。パスワードを含むので秘密として管理 |
| `FMP_API_KEY` | FMP APIキー |
| `LINE_TOKEN` | LINE Messaging APIチャネルアクセストークン |
| `LINE_USER_ID` | 単一の通知先ユーザーID |
| `ADMIN_ID` | 管理者ログインID、1〜100文字 |
| `ADMIN_PASSWORD_HASH` | bcryptハッシュ（cost 12以上） |
| `PUBLIC_ORIGIN` | 公開URLのオリジン。例：`https://stock.example.com`。パス・末尾スラッシュなし |
| `HTTP_ADDR` | Goの待受アドレス。既定`127.0.0.1:8080` |

WebにはDB・FMP・認証・公開オリジン設定、監視コマンドにはDB・FMP・LINE設定が必要。必須設定不足は起動・実行前に失敗させる。LINEの通知先は公式アカウントを友だち追加し、使用契約に必要なアクセス権と送信枠を用意する。

## 定期実行・デプロイ

- 外部スケジューラ側のタイムゾーンを`Asia/Tokyo`に設定し、毎日07:00に`stock-notification monitor`を起動する。UTC指定なら毎日22:00 UTCが翌日の07:00 JSTに相当する。
- 監視全体のadvisory lock・明示的な行ロックによる排他制御は設けない。スケジューラを重複設定せず、手動実行や停止・再開・削除の前に監視コマンドの終了を確認する。個人利用のため運用で競合を避け、同時実行時の通知・更新の整合性は保証しない。
- 監視終了0/1と銘柄単位の処理結果を記録する。失敗・未実行は運用側で検知し、必要時に同じコマンドを手動実行する。停止した実行を自動で過去に遡って再生しない。古いデータの検知は停滞通知成功・自動停止時も終了1。自動停止後はデータ提供状況を確認して必要に応じて手動再開する。停滞通知失敗時は監視中を維持し、翌日の日次処理で再判定する。
- Webのリクエストタイムアウトは90秒、プロキシも90秒以上にする。外部APIの通信は30秒を上限とする。APIの中断時にも既に完了した登録・停止などは反映され得るので、再試行前に一覧を取得する。
- 日次処理中にDB接続が切れた場合は再接続して残処理を継続せず終了1。接続を維持できる対象単位の失敗はロールバックして他対象を続行する。処理済み対象の変更は維持する。
- デプロイ前にDBマイグレーション、管理者ハッシュ設定、秘密情報設定を行い、外部APIを模擬した受け入れ検証を通す。稼働後は認証・一覧・登録、日次コマンドの終了状態を確認する。
- 期限切れセッションは毎日の監視開始時とWeb起動時に削除する。削除される前でも期限チェックによりアクセスは拒否する。
- DBバックアップと復元手順を用意する。DBを復元したらセッションを全削除する。通知済み状態もバックアップ時点へ戻るため、復元後は通知が重複し得ることを運用仕様に含める。

ログは実行ID、監視対象ID、結果、内部エラーコード、終了時刻を記録する。ログイン入力、Cookie、CSRFトークン、接続文字列、外部API URLのキー付きクエリやレスポンス本文は記録しない。
