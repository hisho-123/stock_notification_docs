# 受け入れ条件・検証シナリオ

製品実装時の受け入れ条件と、本仕様書・HTMLを確認する条件を定義する。通知・外部価格取得はモックを用い、実ユーザーへの送信なしで検証する。例示する価格は仮の値。

| ID | 条件 | 期待結果 |

| M-01 | H=100、P=90.0001と90 | 前者は未通知、後者は10%。表示丸めに判定が影響されない |
| M-02 | H=100、P=73、未通知 | 25%について1通のみ、L=25 |
| M-03 | 20%通知後に95→80→100 | 再通知なし、L=20保持 |
| M-04 | 20%通知後に110→99 | 110でH更新・L=null、99で10%通知 |
| M-05 | L=20、設定を[5,15,25]へ変更、P=80→75 | 80は通知なし、75で25%通知 |
| M-06 | 下落通知のLINE送信失敗 | L保持、取得価格・日時とNOTIFICATION_FAILED保存。失敗後の再送などの追加処理なし。翌日の日次実行で最新価格から通常の通知条件を再判定 |
| M-07 | FMP失敗 | 価格・最高値・通知済み率保持、確認時刻とPRICE_FETCH_FAILEDを保存。他銘柄処理継続、終了1 |
| M-08 | 鮮度確認を通過して正常処理へ復帰 | last_error_code=nullに戻る。古いデータ検知や手動再開だけでは解消しない |
| M-09 | DB保存失敗・接続断 | 対象のトランザクションをロールバック、終了1。接続維持なら他対象を続行、接続断なら再接続せず終了。処理済み変更は維持。LINE受付後なら重複リスクあり |
| M-10 | 重複実行を避ける運用 | スケジューラと手動実行が重ならない手順を確認。アプリの排他制御や重複時の正常スキップを前提にしない |
| M-11 | 処理前の存在・有効状態の再確認で停止・削除済み | 保存・通知せずスキップする。確認後の競合については整合性を保証しない |

| M-13 | 実行途中にユーザー別設定を変更 | 実行開始時の当該ユーザーの配列をその所有銘柄で使用。他ユーザーの配列と混同せず、次回から新配列 |

| ID | 条件 | 期待結果 |

| S-03 | ブラウザAPIへの他Origin・Origin欠落、保護APIの変更系CSRF欠落/不一致 | 403、DB変更なし。ログイン・登録・登録確認もOrigin確認。Webhookだけは署名で検証 |

| S-05 | JSON以外・未知項目・不正ID | 415または400。処理しない |
| S-06 | 秘密値を含む外部障害 | 応答・ログにキー、トークン、SQL、レスポンス本文なし |
| S-07 | スケジュール設定 | 日本時間07:00に起動。UTCなら前日22:00との対応を確認 |

## ユーザー登録・LINE連携

| ID | 条件・操作 | 期待結果 |
| --- | --- | --- |
| R-01 | 未登録LINEユーザーが友だち追加 | source.userIdに紐付くハッシュ化トークン1件を保存。LINEトークに24時間・1回限りの登録URLを返信。usersはまだ作成しない |
| R-02 | 有効URLを確認し、ID・パスワードで登録 | 確認はトークン未消費。登録201でusersにlogin_id・password_hash・line_user_id・友だち状態、本人の初期通知率、24時間セッションを作成しトークン消費。自動ログイン、一覧0件 |
| R-03 | 登録から24時間未満・ちょうど・超過、無効・使用済み・失効済みURL | 有効なのは期限未満だけ。利用不可は共通410・同じ案内で、登録やパスワード更新なし |
| R-04 | 使用済みlogin_idで登録して別IDで再送 | 409。ユーザー・設定・セッション追加なし、トークン未消費。別IDなら成功 |
| R-05 | 同じトークンの同時登録、異なるLINEで同じIDの同時登録 | 前者は1件のみ成功・他方410。後者は1件のみ成功・他方409。ユーザー・設定・セッションが部分作成されない |
| R-06 | 同じLINEが「登録」を送信し再発行、別LINEから同じIDを指定 | 再発行で旧URLが410・新URLだけ有効。LINEごとに1ユーザー・IDは全体で一意 |
| R-07 | 登録済みLINEからfollow・「登録」 | ログインURLを返信。既存の銘柄・設定・パスワードを維持し、新規ユーザー・登録トークンなし |
| R-08 | 署名欠落・不一致・署名後の本文変更 | 403 INVALID_LINE_SIGNATURE。登録・友だち状態・履歴の変更なし。正しい署名はOrigin・Cookie・CSRFなしで受理 |
| R-09 | 空events、グループ、userIdなし、未知イベント・未知プロパティ | 空配列と無視対象は200・副作用なし。外部仕様の追加プロパティを理由に400にしない |
| R-10 | 同じwebhookEventIdを再配信 | URLの再発行・二重返信・状態変更なし。200。isRedelivery=falseでも同じIDなら重複扱い |

| R-12 | ユーザー登録・URL再発行・unfollowの競合、途中DB失敗 | LINE単位で直列化。有効な登録URLは最大1件。登録完了または失効が原子的に確定し、中途半端なユーザー・設定なし |

## ユーザー分離・ブロック中の日次処理

| ID | 条件・操作 | 期待結果 |
| --- | --- | --- |
| U-01 | A・Bが同じ正規化コードを追加 | 両方201。本人の再追加だけ409。最高値・監視状態・通知済み率は別レコード |
| U-02 | AがBのデータを検索・件数取得、Bの銘柄IDをPATCH/DELETE | 一覧・件数にBを含めず、操作は404・BのDB不変。要求へのlogin_id/user_id追加は400 |
| U-03 | Aが通知率を変更し、A・Bの同じ銘柄を日次処理 | Aの銘柄だけ新設定を適用。各所有者のusers.line_user_idへ送り、相手の通知先・状態を流用しない |
| U-04 | Aがブロックして、鮮度正常・下落閾値到達 | Aの価格・確認時刻を更新、送信0回・通知済み率保持。抑止だけならNOTIFICATION_FAILEDなし・終了0。Bは通常処理 |
| U-05 | ブロック中に新高値、または古い価格を検知 | 新高値は通常どおりL=null。古い価格は保存済み価格・最高値・取得時刻・L保持、確認時刻更新、PRICE_DATA_STALE、監視中維持・送信0回・終了1 |
| U-06 | ブロック解除後、回復済み／まだ下落／まだ古い価格 | 即時取得・通知なし。次回に最新価格で再判定し、過去の通知は繰り越さない。古い価格の停滞通知受付成功時だけ自動停止 |
| U-07 | 登録前にブロック、または登録済みでブロック | 前者は全URL失効、後者はセッション・銘柄・通知設定を保持。Webログイン・編集は可能 |
| U-08 | Aの設定欠落、Bの設定正常 | Aの設定APIは503。日次処理はAを失敗・スキップしてBを処理、全体終了1。初期値に戻さない |
| U-09 | ログアウト後に別ユーザーでログイン、旧要求が遅延到着 | 旧一覧・設定・CSRF・未保存入力を破棄し、旧応答が新画面へ反映されない |
| U-10 | セッション応答・ログ・URLを確認 | login_idへ統一。LINEユーザーID・password_hashを応答せず、登録URL・トークン・replyToken・入力パスワードをログに残さない |

HTML確認では登録の全状態、入力エラー、UTF-8バイト境界、確認再試行、完了から一覧への遷移を実行する。本仕様書の確認結果は[verification.md](verification.md)に記録する。
