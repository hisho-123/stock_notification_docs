# 関連実装への影響

確認日：2026-11-03。本改訂の成果物は仕様書・OpenAPI・HTML見本。製品のGo・React・DBマイグレーションは変更していない。関連リポジトリは読み取りだけで確認した。

## 参照した現状と既存差分

| 対象 | 確認時点 | 現状 |
| --- | --- | --- |
| stock_notification_docs | d70db88を基に今回改訂 | 単一管理者・全体通知設定・3画面の仕様。本改訂で内部の回復待ちを追加し4テーブルを定義 |
| stock_notification_backend | 36285f0 | 複数ユーザー・LINE登録・Webhook・所有者別設定・送信・ブロック抑止は実装済み。現在6テーブル。通知判定は最終通知済み最大率に依存し、下落の最大閾値のみ送信 |
| stock_notification_frontend | dd0fbc0 | LINE登録画面・login_idのセッション・ユーザー切替時の破棄を実装済み。通知説明と一覧は旧ルールのまま |

仕様書チェックアウトと関連実装の複数ユーザー対応の差は、回復通知追加前から存在する。今回は認証・登録API・所有者列の仕様全体を変更せず、回復通知の追加と区別して記録する。本書の単一管理者用OpenAPIを関連実装の全API契約として上書き・再生成しない。複数ユーザー仕様全体の統合は別の変更で扱う。

## 回復通知に必要な変更

| 領域 | 必要な変更 |
| --- | --- |
| backend：判定・メッセージ | 最大閾値とLによる抑制を、処理前の水準別回復待ちによる下落・回復候補の判定へ置換。全候補を昇順で1通にまとめる。回復基準は保存した最高値を使い、同値を除外 |
| backend：永続化 | asset_recovery_statesを追加。既存6テーブルを保持したまま7テーブルとし、主キー・価格制約・銘柄削除のCASCADEを実装。候補の作成削除と価格・最高値・Lを同一トランザクションで保存 |
| backend：設定保存 | 設定置換と、削除率の回復待ち取消を同一トランザクションにする。停止中も対象。保存失敗では両方戻す。再追加は待ちを復元しない |
| backend：所有者・ブロック | assetsのlogin_idで待ちの参照・変更・設定取消も所有者に限定。送信先は既存のusers.line_user_id。ブロック中は待ちを成功扱いせず、価格・最高値だけ更新。新高値でも旧Bを保持 |
| backend：API | Asset・設定の要求応答・ソート値は増やさない。last_notified_thresholdを表示用へ変更し、NOTIFICATION_FAILEDに回復失敗を含める。内部テーブルをDTOへ公開しない |
| frontend：画面・スタブ | 既存の登録・ユーザー分離を保持し、一覧の見出しを「最終下落通知率」にする。通知設定の説明・例を全水準通知、厳密な回復境界、繰り返し、削除取消へ変更。モック・テストの期待表示も更新 |
| 両実装：検証 | 境界・部分回復・再下落・設定取消・失敗・ブロック・新高値を追加。旧最大率だけの送信・回復後も再通知しない期待値を置換し、ユーザー別の独立性を確認 |

監視の重複起動・実行中の設定変更・停止・削除との排他制御は今回追加しない。運用で重複を避け、競合時の送信取消・更新順序は保証しない。既存の毎日07:00 JST起動・送信先設定方式を継続し、回復専用の環境変数・ジョブは設けない。独立したstock_notification_infrastructureは参照範囲に存在せず、backendのdeploy構成を運用設定の参照元とする。

## 移行・検証の境界

旧データからの待ち復元・データ移行は提供せず、製品実装時は開発DBを再作成する。Lだけでは通知済みの全水準・基準最高値が分からないため、旧Lを回復待ちへ変換しない。

[受け入れ条件](acceptance.md)は製品実装後にモックLINE・FMPと専用DBで実行する。今回の[検証結果](verification.md)は文書・OpenAPI・静的HTMLの確認であり、回復通知の製品実装済みを意味しない。[実装済みテストケース](test-cases.md)と過去の検証記録は改訂前の実績として保持する。
